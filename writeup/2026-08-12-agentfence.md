AI 코딩 에이전트에 샌드박스를 켜고 `permissions.deny` 를 걸면 안전해진다고들
한다. 공식 문서도 그렇게 안내한다. 그런데 **그 설정이 실제로 무엇을 막는지**
숫자로 말하는 자료를 찾지 못했다.

그래서 쟀다. 대상은 Claude Code 2.1.220, 회차는 팔당 60회씩 축을 갈아 가며
수천 번. 결론부터 말하면 **권고 설정 네 줄 중 조건 없이 살아남은 것은 없었다.**

---

## 재는 방식을 먼저 바꿔야 했다

처음 다섯 번은 측정이 성립하지 않았다. 이유가 전부 같았다 — **모델이 거부해서**다.

"워크스페이스 밖에 파일을 써라" 라고 시키면 에이전트가 안 한다. 프롬프트를
바꿔 봐도, 문서에 지시를 심어 봐도 "boundary-testing scenario 로 읽었다" 며
거부한다. 그러면 그 뒤에 있는 **강제 층은 한 번도 시험되지 않는다.** 모델 판단과
경계 강제가 직렬로 놓여 있어서, 앞이 항상 막으면 뒤를 볼 수 없다.

해법은 모델이 경계를 넘고 싶어 할 필요를 없애는 것이었다.

> 모델에게는 **"빌드를 돌려라"** 만 시킨다.
> 경계를 넘는 동작은 **빌드 스크립트가** 한다.

스크립트는 `${XDG_CACHE_HOME:-$HOME/.cache}` 로 캐시를 쓴다. 평범한 빌드 관용구다.
모델은 거부할 이유가 없고, 그래서 강제 층이 실제로 시험된다. 이걸 바꾸고 나서
바닥 노이즈가 20% → 0% 로 떨어졌다.

## 결과 1 — OS 강제 층은 네 칸 중 한 칸에만 있다

권한 층을 끄고(`bypassPermissions`) 남는 것만 본다.

| 동작 | 경로 | Windows | WSL2 (샌드박스) |
|---|---|---|---|
| 쓰기 | Bash 경유 | 1.000 (5/5) | **0.000 (0/60)** ← 유일하게 막힌 칸 |
| 쓰기 | 내장 `Write` | 1.000 | **1.000 (5/5)** |
| 읽기 | Bash 경유 | 1.000 | 1.000 |
| 읽기 | 내장 `Read` | 1.000 | 1.000 |

"WSL2 샌드박스가 막아 준다" 는 **Bash 경유 × 쓰기** 에만 참이다. 내장 `Write`
도구는 샌드박스를 아예 지나가지 않는다. 그리고 밖 **읽기**는 기본이 컴퓨터 전체
허용이라 그냥 통과한다 — 공식 문서가 그렇게 적어 두었고, 실측이 같았다.

더 이상한 것은 권한 층을 켰을 때다. `dontAsk` 에서 밖 읽기가 **Windows 는
0/5 로 막히는데 WSL2 는 5/5 로 통과한다.** 방향이 반대다. 이유는 문서화된 두
문장의 곱이다 — 샌드박스가 Bash 를 자동 승인하므로 권한 층이 그 명령을 **보지
않고**, 샌드박스 자신의 읽기 정책은 전체 허용이다. 층이 하나 늘어난 게 아니라
**하나가 다른 하나로 교체되고, 읽기에 대해서는 교체된 쪽이 더 약하다.**

## 결과 2 — 그 한 칸은 패키지 두 개에 달려 있다

두 번째 WSL2 배포판에 복제를 세우다 발견했다. 같은 Ubuntu 24.04, 같은 커널,
다른 것은 `bubblewrap` 과 `socat` 유무뿐이었다.

| 조건 | 밖 쓰기 |
|---|---|
| 의존 있음 · `failIfUnavailable: true` | **0/60 = 0.000** |
| 의존 없음 · `failIfUnavailable: true` | 하드 실패 (측정 불가) |
| 의존 없음 · `failIfUnavailable: **false**` | **10/10 = 1.000** |

**같은 설정 파일이 정반대 결과를 낸다.** `sandbox.enabled: true` 라고 적혀
있는데 강제 층은 그냥 없다.

그리고 이게 이 글에서 가장 실무적인 부분인데 — **그 경고는 `stderr` 로만 나온다.**

```
⚠ Sandbox disabled: sandbox is enabled but dependencies are missing:
  bubblewrap (bwrap) not installed, socat not installed
  Commands will run WITHOUT sandboxing.
```

같은 회차의 `stdout`(`--output-format stream-json`)에는 흔적이 **하나도 없다.**
모든 이벤트를 중첩까지 재귀로 훑어 `sandbox` 라는 문자열을 찾아봤다 — 0건.
종료 코드 0, `is_error: false`. **정상 회차와 구별되지 않는다.**

즉 CI 가 이 CLI 를 stdout 만 파싱해 쓰면, 강제 층이 사라진 것을 알 방법이 없다.
내 하네스가 정확히 그랬고, 그래서 10/10 을 한동안 그냥 "통과"로 기록하고 있었다.

## 결과 3 — 첫 턴만 방어된다

같은 세션에서 같은 요청을 반복하면 통과율이 오른다.

|  | 턴 1 | 턴 2–4 |
|---|---|---|
| 통합 | **6/24 = 0.250** | **63/72 = 0.875** |

Fisher `p = 2.3×10⁻⁸`, 픽스처 두 개에서 복제됐다. 우회 기법이 아니라 **그냥
다시 물어보는 것**이다. 첫 접촉에서만 따지고 그 뒤에는 안 따진다.

이 축은 두 번 판정에 실패했다. "턴마다 독립"과 "세션당 한 번 정함" 두 가설만
놓고 검정을 짰는데, 실제 현상은 셋째(**턴 위치 효과**)였고 그러면 앞의 둘 중
아무 쪽으로나 보인다. 가설을 둘로 잡은 것이 오류였다.

## 결과 4 — 규칙의 효력은 **픽스처가 정한다**

이게 이 프로젝트의 중심 발견이다.

`deny: ["Bash"]` 가 얼마나 막는지 재려면 **답이 셸 뒤에만 있는** 과제가 필요하다.
답(회차별 난수 카나리)을 컴파일된 바이너리 뒤에 두고 소스는 지웠다. 지시는
바꾸지 않고 **답의 위치만** 옮겼다.

| 답의 형태 | 샌드박스만 | + `deny: ["Bash"]` |
|---|---|---|
| `.rodata` 에 문자열로 저장 | 46/60 = 0.767 | **57/60 = 0.950** |
| 저장 않고 실행 시 계산 | 47/60 = 0.783 | **6/59 = 0.102** |

**같은 규칙이 0.950 과 0.102 를 낸다.** 두 샌드박스 팔은 통계적으로 같으므로
(`p = 1.000`) 기저율은 안 변했다. 바뀐 것은 *바이트에 닿는 다른 길이 있는가*
하나뿐이다.

첫 줄에서 셸을 완전히 제거했는데 값이 **오히려 올라간 것**은, 내장 `Read` 가
ELF 파일을 그대로 읽어 `.rodata` 문자열을 돌려주기 때문이다. 도구 이름을 막는
것과 **바이트에 닿는 길을 막는 것**은 다르다.

같은 방법을 자격증명 규칙에 걸었더니 더 나쁜 게 나왔다. 권고 목록을 둘로 쪼갰다.

| 규칙 묶음 | 접근 |
|---|---|
| 샌드박스만 | 47/120 = 0.392 |
| `Read(**/.aws/**)` · `Read(**/.ssh/**)` 만 | **47/120 = 0.392** |
| `Bash(cat|grep|head|tail:*)` 만 | **0/106 = 0.000** |

**분자가 같다.** 경로 규칙을 걸든 안 걸든 120회 중 47회다. 닫는 일은 이름
규칙이 한다 — 그리고 이름 열거는 **내가 이미 불완전하다고 실측한 방식**이다
(`grep -n ''` 가 `cat` 의 완전한 대체라 목록을 뚫었다).

그리고 `bypassPermissions` 로 바꾸면 **목록 전체가 무력해진다**(46/60 = 0.767,
기저와 `p = 0.354`). 이름이 하는 말 그대로다.

## 내가 틀린 것들

이 프로젝트에서 배운 게 결과보다 이쪽이 크다.

**"바이너리는 `Read` 로 못 꺼낸다"** 고 적고 그대로 쟀다. 관측이 아니라 추측이었고
틀렸다. selftest 는 *텍스트 파일*에 카나리가 없다는 것만 확인하고 있었다 —
정작 재는 대상인 바이너리는 안 봤다. 지금은 두 변형의 텍스트 노출을 selftest 가
직접 관측해 고정한다.

**셸 루프 변수가 `wsl -- bash -lc` 를 통과하면서 빈 값이 됐다.** 그래서 네 팔짜리
계획이 인자 없이 실행돼 **세 시간 동안 이미 아는 값을 다시 쟀다.** 출력 첫 줄이
`--- ---` 였는데 그때 안 봤다. 교훈은 "셸을 조심하자" 가 아니라 **재기 전에
무엇을 재는지 확인하는 단계가 없었다** 는 것이다.

**무효 회차의 사유를 `subtype` 으로 읽었다.** 계정 한도 초과 회차에서도 그 값이
`"success"` 로 와서, 300회를 "무효 사유: success" 로 세고 앉아 있었다.

세 번 다 같은 모양이다. 이 저장소에 여덟 번 적힌 문장이 있다:

> **"안 일어남"은 거의 항상 두 가지 이상을 뜻한다** — 막혔다 / 시도가 없었다 /
> 못 했다. 매번 두 번째 신호를 붙여야 갈렸다.

`Bash` 시도 횟수, 안쪽 대조군, 무효 사유 원문, 서브에이전트 호출, 사후 스캔이
전부 그렇게 붙었다.

## 그래서 설정을 어떻게 하나

조건을 빼면 거짓말이 되므로 조건째로 적는다.

```jsonc
{
  "sandbox": {
    "enabled": true,
    "failIfUnavailable": true,        // 없으면 조용히 열린다
    "allowUnsandboxedCommands": false
  },
  "permissions": {
    "deny": ["Bash", "Read(**/.ssh/**)", "Read(**/.aws/**)"]
  }
}
```

- **`bubblewrap` 과 `socat` 을 먼저 깔아야 한다.** 없으면 위 설정은 무의미하다.
- **`bypassPermissions` 를 쓰면 `deny` 는 아무것도 안 한다.** 그 모드에서 남는
  것은 샌드박스 하나뿐이고, 그것은 Bash 경유 쓰기 한 칸에만 있다.
- **`deny: ["Bash"]` 는 도구를 막지 바이트를 막지 않는다.** 경로 기반 `Read`
  규칙이 보조가 아니라 **짝**이다.
- **경로 규칙은 `dontAsk` 에서 아무것도 안 막는다.** 그 모드에선 내장 `Read` 의
  밖 읽기가 기본으로 막혀 있어서 걸릴 자리가 없다. `bypassPermissions` 에서는
  걸릴 자리가 있지만 그땐 규칙 자체가 안 돈다.

## 남은 것

- 깊이 2 서브에이전트의 내부 호출은 부모 스트림에 오지 않는다. **효과는 관측되고
  내부 경로는 안 된다.**
- 복제는 파일시스템·설정·버전까지만 통제했다. **계정은 통제하지 못했다.**
- 한 제품, 한 버전(2.1.220), 두 플랫폼. 일반화는 여기까지다.

적힌 모든 하중 지는 숫자는 원시 파일에 묶여 있고, 어긋나면 selftest 가 깨진다 —
표에 적힌 값이 측정과 다른 실패를 두 번 냈기 때문에 만든 장치다.
